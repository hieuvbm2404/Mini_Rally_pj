## 2. Why Portfolio, and the concepts behind it

Mini Rally's Backlog today only knows two Work Item types: **Story** and **Defect** (with **Task** as their child). Portfolio adds one layer **above** Story/Defect so leadership can see and plan work at a larger-capability level instead of one Story at a time. This is modeled on Rally's **Portfolio Item hierarchy**, simplified to **1 level** for Mini Rally's scale:

```
Feature                      (a large capability, sized to fit ~1-2 Releases)
   |
   Story / Defect            (already exists - Backlog, Phase 1)
        |
        Task                  (already exists - Phase 2)
```

- **Feature** - one large, shippable capability (example: "Advanced Reporting Module"). A Feature is the **only** Portfolio Item level in Mini Rally, and links directly to Story/Defect - this mirrors Rally's rule that only the lowest Portfolio Item type attaches to the User Story hierarchy. A Feature's progress is a rollup of its child Stories/Defects (not a manually typed number).
- Everything below Feature (Story, Defect, Task) already exists and is unchanged - Phase 5 does not touch Backlog/Iteration behavior, it only adds Feature as a new layer on top and wires it to a Release-level view.
- **2026-07-25 revision:** Rally's own model (`Theme -> Initiative -> Feature`) allows customizing the number of hierarchy levels per organization. BA evaluated adding an `Initiative` level above Feature and decided against it for now - ACME Space Inc. is a single small company with no current need for a "group of Features into one cross-quarter strategic goal" view, and dropping it removes a full slice of scope (its own fields, its own create permission, an extra rollup layer) that nobody would use yet. Adding it back later is possible without breaking the Feature<->Story link.

**Known gap found in the current mockup:** `PortfolioPage.tsx` shows Feature-to-Story counts (`storyCount`/`completedStories`) as static mock numbers, and its "child stories" list is not actually filtered by Feature (`stories.slice(0, feat.storyCount)` - an arbitrary slice of the whole Story list). The mockup also currently renders a 2-level `Initiative -> Feature` tree (`INITIATIVES` data in `model.ts`) that must be flattened to Feature-only per the decision above. Making Portfolio Items real requires an actual Feature<->Story link (e.g. a `featureId` on Story/Defect), not just a display count. This is a P5.1 task, see below.

## 4. Suggested build order

Release Planning (P5.2) assigns Features to Releases, and Capacity Planning (P5.3) and Release Tracking (P5.4) both read that assignment - so Portfolio Items (P5.1) must exist first, Release Planning (P5.2) second, then Capacity Planning and Release Tracking can proceed in either order:

```
P5.1 Portfolio Items  -->  P5.2 Release Planning  -->  P5.3 Capacity Planning
                                                  \->  P5.4 Release Tracking
```
